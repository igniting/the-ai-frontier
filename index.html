01 · Prologue

The brief, and why a compiler

The request was open-ended: show where I am strong at coding. I looked for a project with three properties. It should take many hours of sustained work. Its parts should depend on each other in unforgiving ways. And its correctness should be something a machine can decide, not something I assert.

A compiler has all three. It is a stack of translations, each feeding the next, so a mistake in one stage surfaces in another. A type checker that is slightly too permissive admits a program that later reads a number as a pointer. A code generator that hides one variable from the garbage collector produces programs that run for ten thousand allocations and then crash. Yet a compiler is also unusually testable. Every program it compiles has a meaning that can be computed another way, and the two answers must agree.

I added one constraint: no dependencies. There is no parser generator, no LLVM, no WebAssembly toolkit and no SAT library. Every layer on this page was written in the session, so every layer had to be checked in the session too.

The page has six parts. Part one explains the language and how the compiler turns it into WebAssembly, down to the bits of a value and the garbage collector. Part two covers testing: how to find bugs in a compiler you just wrote. Part three describes three projects built so that a machine can check them: a compiler that compiles itself, rewrite rules with proofs, and a measured performance campaign. Part four uses all of it to prove a theorem, and explains SAT solving and proof checking on the way. Part five starts again: a second language, designed with what the first one taught me, that proves its own array accesses safe, needs no garbage collector, and proves the same theorem. Part six lists what went wrong and what this does and doesn't show.

Part one · contents

The language and its compiler

This part covers what Lumen looks like and how its compiler turns a program into WebAssembly. The compiler infers types, checks pattern matches and flattens nested expressions. It packs every value into a 32-bit word, and it manages memory with a garbage collector that it writes into each binary. The later parts build on these details.

Algebraic data types

type Shape { Circle(Int), Rect(Int, Int), Group(List<Shape>) } declares a type with three variants, each carrying its own fields. A Shape is a circle with a radius, a rectangle with a width and a height, or a group of other shapes, so the type is recursive. In C terms it is a tagged union, except that the language lets you read a variant's fields only after checking which variant you have. Lists are an ordinary type of this kind, defined in Lumen's standard prelude as List<a> { Nil, Cons(a, List<a>) }. The bracket syntax [1, 2, 3] is shorthand for Cons(1, Cons(2, Cons(3, Nil))).

Pattern matching, checked for completeness

match inspects a value, picks the first arm whose pattern fits, and binds the fields to names. Patterns can be nested, and they can match tuples, lists, literals and constructors. The compiler proves that every match covers every possible value. When one doesn't, it builds an example of a value that slips through. Functions are values, and loops are tail calls

|best, s| max(best, area(s)) is an anonymous function, or closure. It can be passed around and called later, and it can use variables from the scope where it was written. x |> f means f(x), written left to right, so parts |> map(area) |> sum reads as a pipeline.

Lumen has no while loop; repetition is recursion. A call in tail position, the last thing a function does, reuses the caller's stack space instead of growing the stack. A loop written as a tail-recursive function can therefore run for any number of iterations in constant stack space.

What it leaves out

Lumen is small by design. It has no floating point, no modules and no exceptions. Strings are immutable byte strings. Integers are 31 bits wide, not 32, for a reason chapter 4 explains. Until part four it had no mutable data at all; arrays arrived when a SAT solver needed them. The full definition is in SPEC.md, which is precise enough for someone to write a second implementation and check it against this one with the included scorer.

03 · Part one

From text to WebAssembly

Background · WebAssembly

WebAssembly, or wasm, is a compact binary instruction format that browsers and standalone engines run at close to native speed. A wasm module is a set of functions. Instructions work on an implicit operand stack: i32.const 2, i32.const 3, i32.add leaves 5 on it. Functions also have numbered local variables (local.get, local.set). Values are a few numeric types; Lumen uses only i32, the 32-bit integer. Memory is one large byte array, called linear memory, read and written by address with i32.load and i32.store, and it can grow at run time.

What wasm does not give you matters as much. It has no strings, lists or closures, only integers and bytes. It does not let a program inspect its own call stack. And Lumen uses no built-in garbage collection: it targets core wasm plus the tail-call extension (return_call) and the bulk-memory instructions, so allocation and collection are the compiler's job.

The compiler is a pipeline of hand-written stages, about 4,000 lines of JavaScript in src/:

  • lexer and parser
  • Hindley–Milner type inference
  • exhaustiveness checking
  • lowering to A-normal form
  • closure conversion
  • pattern-match compilation
  • wasm code generation
  • binary encoder

1 · Lexing and parsing

The lexer turns characters into tokens (fn, sum_to, (, …). The parser builds a syntax tree by recursive descent: one function per grammar rule, with operator precedence handled by the order in which those functions call each other. It also removes syntactic sugar early, so that later stages see a smaller language: [a, ..rest] becomes Cons(a, rest), and x |> f(a) becomes f(x, a). Every node records its position in the source, so error messages can underline the offending expression.

2 · Type inference

Hindley–Milner inference starts by giving every unknown type a fresh variable, then collects equations from how values are used and solves them by unification. For sum_to:

  • n gets the unknown type t1, acc gets t2, and the result gets t3.
  • n == 0 compares two values of the same type, and 0 is an Int, so t1 = Int.
  • Both branches of an if have the same type: the first branch is acc, so t3 = t2.
  • acc + n uses integer addition, so t2 = Int.
  • The recursive call passes (Int, Int) and returns t3, which is consistent.

Result: sum_to : fn(Int, Int) -> Int. Unification itself is short. To make two types equal: if one is an unresolved variable, bind it to the other, after checking that it doesn't occur inside the other (that would be an infinite type). If both have the same outer shape, such as two function types, unify their parts. Otherwise the program has a type error, reported at the expression that produced the equation.

The subtle part is generalization. When inference finishes a function such as pair_up and some variables are still unresolved, those variables can be anything. The compiler marks them generic, and each later use gets fresh copies. That is why pair_up(1) and pair_up("x") can both appear in one program. Two details make this work at scale:

  • Levels. Each type variable records how deeply nested the definition that created it was. A variable can be generalized only if it was created inside the definition being finished, which a level comparison decides without scanning the whole environment. This is the technique OCaml uses.
  • Dependency order. Top-level functions may be written in any order and call each other. The compiler builds the call graph, splits it into strongly connected components (groups of mutually recursive functions), and checks the components in dependency order. Each component is generalized before any function outside it that uses it is checked.

3 · Exhaustiveness

Checking that a match covers every case uses Luc Maranget's “usefulness” algorithm. A pattern is useful after a list of others if some value matches it and none of them. A match is exhaustive exactly when a wildcard _ would not be useful after all its arms. The algorithm works recursively, column by column, through the constructors of each type. When the wildcard is useful, the same recursion builds a concrete value that no arm handles: the (FlashingRed, None) in the error above. Testing each arm against the arms above it also finds arms that can never match, which produce a warning.

04 · Part one

Values, memory and a garbage collector

A Lumen program creates data constantly: every list cell, tuple, closure and string. In wasm, all of it ends up as 32-bit integers and bytes in linear memory. This chapter covers how values are represented, how memory is reclaimed, and the one hard problem wasm poses for a garbage collector.

Every value is one 32-bit word

A variable in compiled code is a single i32. Small values live directly in the word. Anything larger lives in memory, and the word holds its address. The collector and the equality functions must tell the two apart without knowing the type, and the lowest bit does it:

  • Immediates are odd. The integer n is stored as 2n + 1. false and () are 1, true is 3, and a constructor without fields, such as None, Nil or Red, is 2i + 1 for its position i in the type declaration.
  • Pointers are even. Heap objects are aligned to 4 bytes, so their addresses always end in two zero bits.

That bit is why Lumen's integers have 31 bits: one is spent on the tag. Arithmetic needs small corrections, which are the extra instructions in the sum_to listing. Adding two stored values gives (2a+1) + (2b+1) = 2(a+b) + 2, so the compiler subtracts 1. Subtraction adds 1 back. Comparisons need no correction, because 2n + 1 preserves order.

Every heap object starts with a header word: its size, its kind (which constructor, or tuple, closure, string or array), and a 1 in the lowest bit, so headers are odd too. The list [7, 8] is two three-word objects: [header, 15, pointer to the next] and [header, 17, 1], where 15 and 17 are 7 and 8 stored as 2n + 1, and 1 is Nil. A string is a header holding its length, followed by its bytes. A closure is a header, a function index, and the captured values.

Background · Garbage collection

A program that allocates constantly must reuse memory it no longer needs. An object is still needed if the program can reach it, by following pointers from its roots: the variables currently in use. Everything else is garbage. A garbage collector finds the reachable objects and reclaims the rest, so programmers never free memory by hand, and can never free it too early.

Cheney's copying collector

Lumen uses the copying collector C. J. Cheney published in 1970, one of the simplest designs that performs well. The heap is split into two halves, called semispaces. The program allocates in one half by bumping a pointer, so an allocation costs an addition and a comparison. When that half is full, the collector copies every reachable object into the other half, packed together, and the halves swap roles. Whatever was not copied is gone, and the collector never looked at it.

The copying has two phases. First, each root's object is copied into to-space, and the old object's header is overwritten with its new address. This forwarding pointer lets a second reference to the same object find the copy instead of copying it again. Then a scan pointer walks through to-space from the start, object by object. It replaces each pointer field with the address of the field's copy, copying the object first if needed. When the scan pointer reaches the end of the copied data, everything reachable has moved and every pointer is updated. There is no recursion, no mark bit and no free list. The collector is written directly as WebAssembly instructions, in src/runtime.js.

The tag bit does double duty here. A forwarding pointer is an address, so it is even, while a real header is odd: one bit tells a forwarded object from an unforwarded one. Fields work the same way. An odd field is a number and is left alone; an even field is a pointer and is followed.

A collection costs time in proportion to the live data, not the garbage. If a collection leaves the heap more than half full, both semispaces double in size with memory.grow, so a program with a growing data set doesn't spend all its time copying. Chapter 9 tunes that threshold and measures the cost.

The hard part: finding the roots

The collector needs every root, and because it moves objects, it must also update every root with the new address. In wasm, the roots are the local variables of every function currently running. Wasm gives a program no way to read another function's locals, let alone change them, so a pointer held in a wasm local is invisible to the collector. If a collection happens while it is there, the local keeps pointing into the old half of the heap, which the next collection will overwrite.

The standard answer is a shadow stack: a region of linear memory the compiler manages itself. Every function that holds pointers reserves a frame of slots there on entry and frees it on exit. Every variable that can hold a pointer, called a traced variable, lives in a slot. After anything that could trigger a collection, the code reads the variable back from its slot, because the collector may have moved the object and updated the slot. The collector's roots are all the slots between the bottom of the shadow stack and its current top.

Tail calls need one extra rule. A tail call replaces the caller's activation, so the caller pops its frame first and then jumps. Any pointers it passes travel as ordinary wasm arguments, briefly invisible to the collector. That is safe because nothing between the pop and the callee's entry can allocate, and the first thing the callee does is store them in its own new frame.

Types decide which variables need a slot. A variable of type Int, Bool or () can never hold a pointer, so it stays in a fast wasm local and the collector never sees it. Those are the # variables in the IR in chapter 3. A-normal form completes the picture: because every intermediate result has a name, no pointer sits unnamed on wasm's operand stack while an allocation happens. Every pointer is in a named variable, and every pointer-holding variable is in a slot.

New frames need clearing. A frame occupies memory that an earlier call used, so its slots start out holding that call's old pointers. If a collection happened before a slot was written, the collector would treat a stale address as a live object. Every function therefore clears its frame on entry with memory.fill. Chapter 9 makes that cheaper, and chapter 20 shows the checks catching me getting it wrong.

Root handling is the most error-prone part of any compiler with a moving collector. Forget to put one pointer in a slot before one call that allocates, and the program works until a collection happens at that moment, perhaps ten thousand allocations later. Bugs like that are why part two exists.

Testing the compiler

I expected to make mistakes in a project this size, so I built ways to find them before trusting anything. A second, independent implementation defines what each program should do. 05 · Part two

How do you know a compiler is right?

Reading a compiler's source won't convince anyone that it is correct: there are too many interactions. Hand-written tests help, but they check only the cases their author thought of, and the dangerous bugs are the ones nobody thought of. The method that works best in practice is differential testing. Run the same program through two independent implementations and require the same result. When they disagree, at least one is wrong, and the program that shows it is a ready-made bug report.

An oracle: the reference interpreter

The second implementation is a 254-line interpreter that evaluates the typed syntax tree directly. It shares nothing with the compiler's back end. It has no IR, no closure conversion, no pattern-match compilation and no value tagging, and it relies on JavaScript's memory instead of a garbage collector. It does share the parser and the type checker, which decide which programs are legal. It implements the rules the compiled code must match:

  • integers wrap around at 31 bits;
  • evaluation is strictly left to right, so the function before its arguments and the left operand before the right;
  • equality is structural, and fails only when it reaches a function;
  • tail calls run in constant stack (the interpreter uses a trampoline, a loop that keeps calling the next function itself instead of nesting);
  • runtime errors, such as division by zero, carry the same messages.

Because it is simple, the interpreter is much easier to trust than the compiler. It is also slow, which doesn't matter for an oracle.

Sharing the front end has a cost: a bug in the parser or the type checker affects both sides alike, so differential testing cannot see it. Two other things cover those stages. Hand-written tests exercise each language feature and error message. And chapter 7 adds a second front end, written separately in Lumen, which must produce the same syntax trees, types and error messages.

Random programs, well-typed by construction

The test programs come from a generator (fuzz/generate.js), and a naive one is useless: random text is almost never a valid program, so it tests only the parser. Lumen's generator is type-directed. To produce an expression of type Int, it picks one of the ways to make one: a literal, an Int variable in scope, arithmetic on two smaller Int expressions, a match on a generated Option, a call to a generated function that returns Int, and so on. It recurses within a size budget, so every program is well-typed by construction. Recursion in the generated program is bounded by small counters, so every program terminates.

Runtime errors are allowed: a generated program may divide by zero or index past the end of a string. The compiled code must then fail at the same point, with the same output before the error. The generator favours the values where bugs live: 0, −1, the largest and smallest integers, empty strings and lists, and multi-byte characters.

Five ways to run each program

Each generated program runs five ways, and all five must agree to the byte:

  1. in the reference interpreter;
  2. compiled to wasm;
  3. compiled with GC stress (GC for garbage collection): a 4 KiB heap and a collection on every allocation. A missing root normally causes trouble only if a collection happens at the wrong moment. Under GC stress every moment is that moment. The collector also overwrites the space it just left, so a dangling pointer reads garbage at once;
  4. compiled with -O, the optimizer from chapters 8 and 9;
  5. compiled with -O and GC stress, in a paranoid mode where frames are poisoned when they are freed and the collector validates every root it sees.

The method has blind spots. The fuzzer skips programs that the interpreter cannot finish within a step budget or that overflow its stack, so only hand-written tests and the benchmarks cover deep recursion. Generated programs are small, so bugs that need a large heap are left to GC stress, which makes even small programs collect constantly, and to the benchmarks. And the fuzzer cannot test what the generator never produces. Finding those gaps is the job of the planted bugs below.

  prints the right answer. GC stress and the paranoid mode exist to turn “usually” into “never”.

07 · Part three

  
The compiler compiles itself

  
A compiler is self-hosting when it is written in the language it compiles. Most mature compilers are:
  the Rust compiler is written in Rust and the Go compiler in Go, while GCC and Clang are written in C++. Reaching
  that point is a classic milestone. A compiler is a large, demanding program, so compiling itself exercises nearly
  every feature of the language, and the generated code has to be right for the result to work at all.

  
For Lumen it is also a test. The rewrite must produce, for every program, the same bytes as the JavaScript
  compiler. Two implementations that agree byte for byte on everything check each other.


  
Writing a compiler in a language with no mutation

  
At this point Lumen had no mutation, no arrays and no hash maps, and local functions could not be mutually
  recursive. The JavaScript compiler relies on all of those, so the port was a redesign:

  
    
    
  • Type inference without mutation. The JavaScript type checker solves unification by updating type
    variables in place: a union-find structure. In Lumen the solution became an explicit substitution, a map from
    variables to types, threaded into and out of every function of the type checker.
    • 
    
  • Maps became balanced trees. Symbol tables and substitutions are persistent AVL trees: inserting
    returns a new tree and leaves the old one intact.
    • 
    
  • The output became a rope. Building a large binary by repeated string concatenation would be
    quadratic. The emitter builds a tree of byte strings with cached sizes and flattens it once. Wasm needs many
    sizes written before the content they measure, and cached sizes make that cheap. My first rope printer was
    recursive and overflowed the stack on large outputs, so it became an explicit loop.
    • 
  

  
I did not write all 3,362 lines and then start debugging. I first built a tool that compares any single
  phase with the JavaScript compiler's output for the same program, then brought the phases up one at a time:
  tokens, syntax trees, inferred types, intermediate code, and finally binaries. When a phase disagreed, the tool
  pointed at the first difference. One mismatch along the way was not a bug in either compiler: the JavaScript
  tools counted source positions in UTF-16 code units and the Lumen ones in bytes, which differ on any non-ASCII
  character.

08 · Part three

  
Rewrite rules that come with proofs

  
Look again at the start of the sum_to listing: a comparison, four instructions to pack its
  result into a Lumen boolean, two more to unpack it. Removing waste like that is the job of a peephole
  optimizer, which replaces short sequences of instructions with cheaper equivalents. Peephole rules are usually
  written by hand, and they are a classic source of bugs. “Equivalent” must hold for every input, including overflow
  and the sign bit, and people are bad at checking that.

  
The alternative is a superoptimizer, an idea from Henry Massalin's 1987 paper: search mechanically for
  the shortest instruction sequence that computes the same function. A search only finds candidates that work on
  the inputs it tried. Mine therefore accepts a rewrite only with a proof that the two sequences agree on all
  2³² values of each input, and a second program checks that proof.


  
Mining and searching

  
The superoptimizer starts from real compiler output. It compiles the example programs and 60
  random programs, cuts their wasm into short windows of straight-line integer code, and counts identical shapes:
  527 distinct windows appeared at least twice. For each window it enumerates candidate replacements in order of
  increasing length. Each candidate runs on 48 test inputs, which mix edge values such as 0, −1 and the extremes
  with random ones. A candidate that matches the original on all 48 goes on to a proof.


  

    
Background · SAT

    
A Boolean formula in conjunctive normal form (CNF) is an AND of clauses, where each clause is an OR
    of literals, and a literal is a variable or its negation: for example (x ∨ ¬y) ∧ (y ∨ z) ∧ (¬x ∨ ¬z). The
    SAT problem asks whether some assignment of true and false to the variables makes every clause true. It
    was the first problem proved NP-complete, so no known algorithm is fast on every input. Yet modern SAT
    solvers routinely handle formulas with millions of clauses from real problems: hardware verification,
    scheduling, package dependencies, and the mathematics in part four.

    
The two answers are not alike. If a formula is satisfiable, the solver can show an assignment, and anyone
    can check it by plugging it in. If it is unsatisfiable, the claim is that no assignment out of 2ⁿ works,
    and checking that requires a proof. Chapter 13 explains how such proofs work.

  


  
From instructions to a formula

  
Before a SAT solver can compare two instruction sequences, they must become Boolean formulas, a step called
  bit-blasting. A 32-bit value becomes 32 Boolean variables, one per bit, and each instruction becomes a
  circuit over those bits. Bitwise AND, OR and XOR work bit by bit. Addition is a ripple-carry adder, in which each
  output bit is an XOR of two input bits and a carry. A shift by a constant just re-wires bits, and comparisons are
  built from subtraction.

  
Each gate of the circuit then becomes a few clauses, by the Tseitin transformation. An AND gate
  g = a ∧ b, for instance, becomes (¬g ∨ a) ∧ (¬g ∨ b) ∧ (g ∨ ¬a ∨ ¬b). Identical gates are shared, so
  when both sequences build the same circuit, the proof is immediate.

A SAT solver is a complicated program, and mine was written in the same session as everything else. If it

  learns while searching, and a separate, much simpler proof checker re-derives each one from the formula. The checker
  shares no code with the solver. A rule is accepted only if its proof checks. Chapter 13 explains how that
  checking works, because the theorem in part four relies on the same checker.

  deliberately naive checker to cross-check it. On the first test they disagreed, and the naive one was wrong: it

What it found

  for: when a comparison's result is packed into a Lumen boolean and the next instruction unpacks it,
  cmp, 1, shl, 1, or, 1, shr_u is just cmp. Six of seven instructions disappear. Others
  are smaller. (x < 0) << 1 | 1 becomes x >>> 30 | 1. And
  (4 − x) >>> 1 == 0 becomes x == 3, but only when x is odd. The
  compiler knows which locals always hold tagged integers, and therefore odd values, and the prover is allowed to
  use that fact.

  
Constants can be generalized too. Instead of proving one rule for x − 3 + 1, the search proves
  (x − K0) + K1 ⇒ x − (K0 − K1) with K0 and K1 as symbols, so the proof
  covers every pair of constants at once. Some rules hold only under a condition such as K ≥ 0. Then
  the condition is part of the proof, and the compiler checks it before rewriting.

  
What the proofs cover, and what they don't

  
Each proof shows that two short instruction sequences compute the same 32-bit result for every input. It does not cover the code that applies the rules: the matcher that finds a
  pattern in a function, checks a side condition and splices in the replacement. That code is tested like the
  rest of the compiler. The fuzzer exercises it, and a planted bug that swaps a proved rule for a subtly wrong one
  is caught after 10 programs. Nor do the proofs cover -O's other passes in the next chapter, such as
  removing temporaries or stack frames. Those are tested, not proved. The proofs cover these 40 rules and nothing
  else.

The problem: Schur numbers

  
Before choosing a problem, I measured candidates. A good one had to be a real theorem with a computational
  proof, small enough to prove in minutes with a solver written from scratch. The party problem, the Ramsey number
  R(4,4) = 18, failed that test: proving its impossible half did not finish in five minutes without extra symmetry
  arguments. Schur numbers passed.

  
Put each of the numbers 1, 2, …, n into one of k groups so that no group contains two numbers and
  their sum, that is, no x, y and x + y all in the same group, where x and y may be equal. What is the largest n for
  which this is possible?Issai Schur, 1916. The answer is called the Schur number S(k).

  
A group with no x, y, x + y inside it is called sum-free. Since x may equal y, a sum-free group cannot
  contain both a number and its double. With one group, you can place 1, but 2 = 1 + 1 has nowhere to go, so
  S(1) = 1. With two groups, try it yourself:

With two groups you can place 1 to 4, for instance {1, 4} and {2, 3}, but never 5. You don't have to try
  everything to see why. Put 1 in group A. Then 2 = 1 + 1 must go to B, and 4 = 2 + 2 must go back to A. Now 3
  can't join A, because 1 + 3 = 4, so it goes to B. And 5 has nowhere to go: in A it would complete 1 + 4 = 5, in
  B it would complete 2 + 3 = 5. Every step was forced, so S(2) = 4. With three groups the game ends at 13, but the
  reasoning no longer runs in a straight line: some placements have to be guessed and later undone. Deducing and
  guessing are the two things a SAT solver does, and chapter 12 returns to them.


  
Why Schur asked

  
Schur's interest was not the puzzle. He was working on Fermat's Last Theorem, which says that
  xᵐ + yᵐ = zᵐ has no solutions in positive integers for m ≥ 3. A natural line of attack is to show there is no
  solution modulo some prime p. In 1916 Schur showed that this cannot work: for every m, the congruence
  xᵐ + yᵐ ≡ zᵐ (mod p) has solutions with none of x, y, z divisible by p, for every large enough prime p. The heart of
  his proof was this lemma: however you split 1 to N into k groups, if N is large enough, some group contains x, y
  and x + y. So S(k) is finite for every k. It is one of the earliest results in what is now called Ramsey theory:
  complete disorder is impossible, and large enough structures always contain some order.

  
Finding the actual values is hard. S(3) = 13. S(4) = 44 was found by computer search in 1965. S(5) = 160 was
  settled only in 2017, by Marijn Heule, with a SAT solver and a proof of about two petabytes. S(6) is still
  unknown.


  
What proving S(4) = 44 takes

  
The statement has two halves of very different difficulty:

  
    
    
  • 1 to 44 can be split into four sum-free groups. One example settles this, and anyone can check it by
    hand, or by a ten-line program. Finding the example is the hard part; checking it is easy.
    • 
    
  • 1 to 45 cannot. This is a claim about every possible split, and there are 4⁴⁵, about
    1.2 × 10²⁷, of them. Even after the symmetry argument in the next chapter, which fixes where 1 and 2 go, 4⁴³ ≈
    7.7 × 10²⁵ remain. Checking a billion per second would take about 2.5 billion years.
    • 
  

  
Brute force is out. The second half needs a search that rules out whole families of splits at once, and it
  must leave behind evidence that can be checked independently. SAT solvers do both.

Turning a question into a formula

  
To use a SAT solver, the question has to become a formula in the form described in chapter 8: an AND of
  clauses, each an OR of variables or their negations. The translation, called the encoding, is short.

  
Variables. One Boolean variable for each number and group: x(i, c) means “number i is in group
  c”. For 45 numbers and 4 groups that is 180 variables.

  
Clauses. Three kinds:

  
    
    
  1. Every number is in some group: x(i, 1) ∨ x(i, 2) ∨ … ∨ x(i, k), for each i.
    2. 
    
  2. No group contains x, y and x + y: ¬x(x, c) ∨ ¬x(y, c) ∨ ¬x(x + y, c), for each group c and each
    x ≤ y with x + y ≤ n. Read it as “at least one of the three is not in group c”. When x = y it has two
    literals: ¬x(x, c) ∨ ¬x(2x, c).
    3. 
    
  3. Symmetry: x(1, 1) and x(2, 2), two clauses of one literal each.
    4. 
  

  
The formula never says that a number is in at most one group, because it doesn't need to. If the solver
  puts a number in two groups, deleting it from one of them can't create a sum, so any such solution yields a
  proper split. Leaving those clauses out keeps the formula smaller.

  
The symmetry clauses rest on one observation: groups are interchangeable, so renaming them turns a valid split
  into another valid split. Without loss of generality, then, 1 is in group 1. Then 2 = 1 + 1 cannot be in group 1,
  and the remaining groups are still interchangeable, so 2 may be put in group 2. This shrinks the space of
  assignments sixteenfold, from 4⁴⁵ to 4⁴³. It is the one step of the whole proof that is argued rather than checked
  by a program.

  
For four groups and 45 numbers, the formula has 45 clauses of the first kind, 4 × 506 of the second and 2
  of the third: 2,071 clauses in all. Solvers exchange formulas in a plain-text format called DIMACS: a header
  p cnf variables clauses, then one clause per line, as variable numbers ending in 0, with
  a minus sign for “not”. For the small case, 1 to 5 in two groups, the Lumen encoder writes this complete

How a SAT solver searches

  

    
Background · Unit propagation and backtracking

    
Suppose some variables already have values. A clause in which every literal but one is false can only be
    satisfied by making that last literal true. Such a clause is called unit, and setting its last literal
    is unit propagation. It is pure deduction: nothing is guessed. Propagation often cascades, since each
    new value can make other clauses unit, and it can end in a conflict, a clause with every literal
    false.

    
The classic search algorithm, DPLL (Davis, Putnam, Logemann and Loveland, 1962), alternates the two moves.
    Propagate as far as possible; if nothing is forced, pick an unassigned variable and guess a value; on a
    conflict, undo the most recent guess and try the other value. Every modern solver still has this loop at its
    core.

  

  
The hand argument for S(2) = 4 in chapter 10 was unit propagation, step for step. Traced over the clauses of
  chapter 11, it reads:

Learning from conflicts

  
For three groups and 14 numbers, propagation stalls before reaching a conflict, and the solver must guess.
  Plain backtracking would then explore the same dead ends over and over, because it forgets why each guess
  failed. Conflict-driven clause learning (CDCL) fixes that: when a conflict happens, the solver works out
  why, and writes the reason down as a new clause. The idea appeared in the GRASP solver in the late 1990s,
  was made fast by Chaff in 2001, and is what made SAT solvers practical. It works like this:

  
    
    
  • Every value remembers its reason. A guessed value has none. A propagated value remembers the clause
    that forced it. Values are grouped into levels: each guess starts a new level, and everything propagated
    from it belongs to that level.
    • 
    
  • Analysis walks backwards from the conflict. The conflicting clause is false. Each of its literals
    is false because of some reason clause. Replacing a literal with its reason (a step called resolution) gives a
    new clause that is still false under the current values and still follows from the formula. The solver repeats
    this until exactly one literal from the latest level remains. That literal is the first unique implication
    point, the single assignment at this level through which every path to the conflict passes.
    • 
    
  • The result is learned. The final clause is added to the formula. It is a logical consequence of the
    original clauses, so it never rules out a real solution. But it rules out every assignment that would fail for
    the same reason, not just the one that was tried.
    • 
    
  • Then the solver jumps back. It undoes guesses back to the level where the learned clause becomes unit,
    possibly many levels at once, and propagation immediately takes the other branch.
    • 
  

  
If analysis ever produces the empty clause, a clause with no literals, the formula itself implies
  “false”: it is unsatisfiable, and the search is over. The Lumen solver's refutation of 1 to 14 in three groups
  ends with the lines below. In this formula, variable 3(i − 1) + c means “i is in group c”:

  

  
The engineering that makes it fast

  
Four further ideas turn the algorithm into a fast solver. The Lumen solver uses all four.

  
    
    
  • Watched literals. Propagation is where solvers spend most of their time, and checking every clause
    after every assignment would be hopeless. Each clause instead watches two of its literals that are not false.
    Only when a watched literal becomes false does the solver look at the clause, to find another literal to watch,
    or to discover that the clause has become unit. Undoing assignments needs no bookkeeping at all.
    • 
    
  • Activity-based decisions (VSIDS, for “variable state independent decaying sum”). Every time a
    variable takes part in a conflict, its activity goes up, and older bumps fade. The solver always guesses the
    most active variable, kept at the top of a heap. In effect, it concentrates on whatever part of the problem is
    currently hard.
    • 
    
  • Restarts. Every so often the solver abandons all its guesses and starts again, keeping everything it
    learned. Here the intervals follow the Luby sequence, 1, 1, 2, 1, 1, 2, 4, 1, …, in units of 100 conflicts.
    Restarts stop the solver from sinking too much time into one unlucky early guess.
    • 
    
  • Phase saving. When a variable is guessed again, it gets the value it had last time, so a restart
    doesn't throw away partial progress.
    • 
  

  
Unlike production solvers, this one never deletes learned clauses. Those solvers regularly discard clauses
  that have stopped being useful, because every kept clause slows propagation. Keeping all of them costs
  speed, but it keeps the proof simple, as chapter 13 shows, and at 255,663 clauses for S(4) it is still

Checking the proof without trusting the solver

  
A solver that says “satisfiable” hands over an assignment, and checking it is trivial. A solver that says
  “unsatisfiable” is asking to be believed, and solvers have bugs. This one was written in a language that did not
  exist when the session began, and compiled, with optimizations, by a compiler written in the same session. If the
  result rested on all of that being right, it would not be worth much.

  
The solver therefore doesn't just answer. It prints every clause it learns, in order, ending with the empty
  clause. That list is the proof, in a standard format called DRUP, for “delete reverse unit propagation” (this
  proof deletes nothing). Each learned clause can be verified on its own, by a simple procedure called
  reverse unit propagation (RUP):

  
    
    
  1. Take the next clause from the proof, say a ∨ b ∨ c.
    2. 
    
  2. Assume it is false: set a, b and c all to false.
    3. 
    
  3. Run unit propagation over the original formula plus every clause already accepted.
    4. 
    
  4. If propagation reaches a conflict, the assumption was impossible, so the clause follows. Accept it and
    move on. If not, reject the whole proof.
    5. 
  

  
Every clause the solver learns passes this test, because conflict analysis produces only clauses that unit
  propagation can confirm against the clauses the solver had at the time. The solver never deletes a clause, and
  the checker keeps every clause it accepts, so the checker always has at least those clauses available. It never
  needs to know how the solver found a clause, only that the clause follows. At the empty clause there is nothing to
  assume, so the checker just propagates. For 1 to 5 in two groups, that propagation is the trace in chapter 12,
  which is why the one-line proof 0 is complete.

  
The checker, superopt/rup.js, is 86 lines of JavaScript. It was written for the superoptimizer's
  proofs in chapter 8 and shares no code with either solver. It was itself cross-checked against a deliberately
  naive implementation, on real proofs and on proofs corrupted on purpose.

Two optimizations the solver led to

  
The SAT solver was the most demanding program Lumen had run, so it became a new benchmark, and profiling it
  suggested the next two optimizations.

  
Arrays, inline. The profiler showed 24% of the solver's work inside the runtime's array functions:
  a call, a bounds check, a load, a return, for every array read. Under -O, array reads and writes are
  now compiled in place: compare the index with the length stored in the header, then load or store.

  
No frame where nothing can collect. The solver has many tiny accessor functions, such as one
  that returns the assignment array from the solver record. Each one pushed a shadow-stack frame on entry and
  popped it on exit, as chapter 4 requires of any function that holds a pointer. But the frame exists only so
  the collector can find and update that pointer, and a collection can only happen during an allocation. If
  nothing a function does while it is running can allocate, its pointers can stay in plain wasm locals. The
  analysis has to be careful about calls, and at first I wasn't. Two properties are involved:

  
    
    
  • Call a function never-collecting if calling it can never trigger a collection, including through
    anything it calls, tail calls included.
    • 
    
  • A function needs no frame if it allocates nothing and every call it makes that is not a tail call is to a
    never-collecting function. A tail call may collect, because by then the function's own activation is
    gone.
    • 
  

  
My first version asked only the second question and used its answer for both. The prelude's
  reverse qualifies for having no frame: its only call is a tail call to rev_append,
  which allocates. But append calls reverse and then carries on using its other argument.
  Treating reverse as never-collecting let append drop its frame while that argument was
  still live, and a collection inside rev_append then moved the list out from under it. The paranoid
  mode from chapter 5 caught it on one of the test suite's fixed random programs, as an invalid pointer on the
  shadow stack, before anything was committed. The two properties are now computed separately, in the same way.
  Start by assuming that every function qualifies, then repeatedly remove any function that breaks the rule under
  the current assumptions, until nothing changes. What remains is the largest set consistent with the rule,
  which handles recursion without special cases. A planted copy of the original mistake is among the 34 bugs the
  fuzzer must catch.

  
Together the two changes cut the solver's executed instructions by 30% and its running time by 27% on the
  search for a split of 1 to 44. It prints a byte-identical 255,663-step proof. Every other benchmark except
  fib executes fewer instructions too; this is step 9 in chapter 9.

Starting again: Lumen 2

  
The question was: “If you had to come up with an even better language spec, what language would you create
  and why?” My answer started from what building Lumen had taught me. Three things about it bothered me.

  
    
    
  • Its types don't say what a function does. fn(List<Int>) -> Int could print,
    read input, or stop with an error on an empty list. The type says nothing about any of that, and the reader has
    to look inside.
    • 
    
  • Its safety checks happen at run time. Every array access and every division is checked as the
    program runs. The SAT solver in Part four performs millions of bounds checks that can never fail. I knew that,
    but the language gave me no way to say it, and the compiler no way to use it.
    • 
    
  • Its memory model fought the problem. The garbage collector in chapter 4 was the hardest part of the
    compiler to get right. A copying collector also can't update anything in place, so the SAT solver needed
    mutable arrays, a language change (chapter 12) that gave up some of Lumen's purity.
    • 
  

  
Testing had taught me two more lessons. Properties like “reversing a list twice gives it back” lived in
  external tools rather than in the language. And the compiler's output was trusted except where tests happened to
  look.

  
So Lumen 2 is a pure functional language like Lumen, with the same kind of type inference, compiled to
  WebAssembly with no dependencies, and checked against a reference interpreter. Beyond that it is a fresh design.
  It shares no code with Lumen, and Lumen is unchanged. The new parts, one sentence each:

  
    
    
  • Effects in types. A function's type lists what it can do: print, read input, read the clock, use
    random numbers, or fail. All of it is inferred.
    • 
    
  • Capabilities. Whoever runs a program decides which of those main may use.
    • 
    
  • Proved operations. An array access or a division can fail only where the compiler cannot prove it
    safe. Refinement types such as {i: Int | 0 <= i} state the facts a proof needs.
    • 
    
  • No garbage collector. The compiler inserts reference counting itself, and a value nothing else refers
    to is updated in place.
    • 
    
  • Certified passes. On every compile, independent checkers re-check the compiler's own output.
    • 
    
  • Traits and properties, and 64-bit integers that stop with an error on overflow instead of
    silently wrapping around.
    • 
  

  
The compiler is about 6,000 lines of JavaScript in
  lumen2/, and the
  language is defined in its own spec.

Background · Effect types

    
The checker extends the unification of chapter 3 to sets of effects. An effect set is written as a list of
    labels, optionally followed by a variable that stands for “and possibly more”, so {output | e}
    means “output, and whatever e turns out to be”. Unifying two such rows matches the labels
    they share and lets each variable absorb the labels only the other side has. Inference stays fully automatic,
    and every function still gets its most general type. The technique is called row polymorphism. Lumen 2's
    version follows Koka, a research language from Microsoft Research.

  


  
Three runtime errors are deliberately not effects: integer overflow, running out of memory, and a string too
  long. Any arithmetic can overflow, so tracking it would put fail on nearly every function and make
  the effect meaningless. Overflow still never produces a wrong answer, because integers are 64 bits wide and
  every operation checks.


  
Capabilities

  
An effect in a type is a statement about the code. A capability is a decision about running it:
  whoever runs a program grants main the effects it may use. The command line grants
  output by default, and --allow random adds randomness. A program that would use an
  effect it was not granted is rejected before it runs, with the error placed on the call responsible. The
  ungranted program in the demo is refused at roll(), not at some library function three calls
  deeper.

  
The clock and random numbers come from a host that the interpreter and the compiled code share, so a
  seeded run is reproducible. That matters for testing. The fuzzer can generate programs that read the clock and
  roll dice, and still demand that the interpreter and the compiled code print the same thing.


  
Traits and properties

  
Lumen compared values structurally, field by field. Lumen 2 adds traits. A user's impl Ord
  replaces structural ordering wherever its type is compared, including inside lists and options, and
  show is derived for every type without functions in it. Methods are resolved at compile time, so a
  trait costs nothing at run time. The checker infers trait requirements too. A tree insert gets
  fn(Tree<a>, a) -> Tree<a> where a: Ord, and sorting a list of functions is a compile
  error, where in Lumen it was a runtime error.

Facts along a path

  
The checker walks each function and keeps a list of facts that hold at each point. Facts come from the
  conditions of the ifs on the current path, from refined parameters, from the results of refined
  functions, and from operations that have already succeeded: after array_get(a, i) returns, the
  index was in bounds. It also knows that an array's length is never negative. Each partial operation becomes a
  proof obligation: do the facts imply that the operation is safe? For the access in

From an obligation to a SAT problem

  
An implication holds when its premises and the negation of its conclusion can't all be true at once. So the
  checker asks a SAT solver, the kind of program Part four explained, whether there are integers that satisfy
  the facts and violate the goal. Here that means 0 ≤ n, 0 ≤ i, i < n,
  and also i < 0 or i ≥ n. If the solver proves that unsatisfiable, the access is
  safe.

  
A SAT solver knows only true and false, so the integers have to become booleans. This is called
  bit-blasting. Each integer variable becomes a vector of boolean variables, one per bit, in two's
  complement. Each operation becomes a circuit written as clauses, in the style of chapter 11. An addition is a
  chain of full adders, where each output bit and carry is a few clauses over the input bits. A comparison
  a < b becomes a − b < 0: a subtraction, then a look at the sign bit. The vectors are about 66 bits wide, wide enough that no sum of
  64-bit values in an obligation can overflow, so the bit-level arithmetic agrees with real integer arithmetic.
  Even this small obligation comes to 2,801 clauses.

Refinement types carry facts across calls

  
The checker does not infer facts about a function's callers or loop invariants. A recursive function that
  walks an array needs to say what it relies on, and a refinement type says it:

  
  
{i: Int | 0 <= i} is an Int that is known to be non-negative. Inside the
  function it is a fact, so the access is safe: 0 ≤ i comes from the type, and
  i < array_length(a) from the if. At every call, it is an obligation. The recursive
  call passes i + 1, and 0 ≤ i implies 0 ≤ i + 1. A caller that passes
  0 is fine, and a caller that passes -1 gets a compile error. A result can be refined
  too: -> {r: Int | 0 <= r && r < n} is proved at the end of the function's body and
  assumed by every caller. A refinement that cannot be proved is always an error. An access that cannot be
  proved just keeps fail in its function's type.

Not trusting the prover

  
A wrong proof would be worse than no proof, because the compiler drops the run-time check for a proved
  access. So the proofs are checked twice. Each refutation passes the RUP checker before the compiler uses it.
  And the reference interpreter re-checks every proved fact as the program runs, while the compiled code does not.
  If a proof were wrong, the two would disagree on some program, and the fuzzer would see it. Two of the planted
  bugs in chapter 18 test exactly this: a checker that assumes an if's condition in its
  else branch too, and an adder circuit that drops its carry. The run-time re-check catches both.

  
The checker has clear limits. Its facts are linear arithmetic over integers and array lengths. It knows
  nothing about list lengths or array contents, and it never invents an invariant. In the SAT solver of chapter 19,
  it proves 19 of the 20 divisions safe, and all of the input parser's indexing. It does not prove the 27 accesses
  to the solver's state arrays, because those depend on facts about array contents, such as every literal in every

Memory without a garbage collector

  
Lumen's copying collector, from chapter 4, finds live objects by following pointers from the roots, and it
  needs the shadow stack to know where the roots are. Lumen 2 has no collector. Every heap object carries a count
  of the references to it, and it is freed the moment the count reaches zero.


  

    
Background · Reference counting

    
With reference counting, copying a pointer increments the count of the object it points to, and discarding
    one decrements it. At zero, the object is freed, and the counts of everything it points to are decremented in
    turn. Memory is reclaimed promptly and without pauses. It has two classic costs. The counting itself is work
    on every copy, and objects that point to each other in a cycle keep each other's counts above zero forever. In
    Lumen 2 the second can't happen: values are immutable, so a value can only point to values that existed before
    it, and no cycle can form.

  


  
The first cost is where the compiler comes in. Lumen 2 follows Perceus, an algorithm published in 2021 by
  Microsoft Research for the Koka language. The compiler, not a runtime library, decides exactly where each count
  changes. The rule is ownership. Each variable holds one reference. The last use of a variable hands that
  reference on, for example to the function it is passed to, at no cost. Any earlier use that hands a reference
  on must first make a new one, with dup. A variable that is dead releases its reference with
  drop immediately after its last use, not at the end of its scope, so memory is freed at the
  earliest possible moment.

  counting, slightly simplified from what lumen2 ir prints:

The same rule applies to arrays. array_set on an array that nothing else refers to writes in
  place, and on a shared array it copies first. Values never change from the program's point of view, yet a
  program that holds its data uniquely pays the cost of mutation, not of copying. Nothing visible decides this:
  it follows from whether the program uses the old value again.

Borrowing and moving

  
Two further optimizations matter for speed. A parameter that a function only reads, never stores or
  passes on, is borrowed. The caller keeps its reference for the duration of the call, so neither side
  counts anything. The compiler infers which parameters qualify. And when a function takes apart a cell that
  nothing else refers to, it can move the fields out (unpack) instead of taking a new reference
  to each field and then releasing the cell. Chapter 19 shows how much each of these was worth.


  
Checking it

  
Reference counting fails quietly. Freeing too early usually works anyway, because freed memory still holds
  its old contents until something else is allocated there. Freeing too late is just a leak. So the test harness
  makes both loud. Every compiled run that finishes must report zero live objects, which catches leaks. And a
  paranoid mode never reuses freed memory and stops the program on any access to a freed object. The
  fuzzer runs every program four ways: interpreted, compiled, compiled in paranoid mode, and compiled without
  reuse. All four must print the same output.

A compiler that checks its own output

  
Part two tested Lumen's compiler on random programs, and Lumen 2 is tested the same way. But a test
  can only cover the programs it tries. Lumen 2 adds a second kind of check that runs on every compile, for every
  program. The compiler's output is re-checked by independent code before it is used, and the compile fails if a
  check fails. This is a light form of an idea called translation validation: instead of proving the
  compiler correct for all programs, check its result for this one.

  
There are two checkers, in
  lumen2/src/certify.js,
  plus the proof checker and the engine's own validation of the final WebAssembly:

  
    
    
  • The IR type checker re-types every instruction after monomorphization, inlining and simplification,
    from scratch. A field read must have the type of that field, and a call must match the signature of the
    function it calls. A pass that confuses two variables or two types is caught here.
    • 
    
  • The ownership checker follows every path through every function. It tracks how many references each
    variable holds, which values are borrowed and from what, and which cells are waiting to be reused. It rejects
    a program that gives away a reference it does not hold, or reads a value after its last reference was
    released. It also rejects returning while still holding references (a leak), two branches that end holding
    different references, and a reuse cell that is neither used nor freed. It encodes the rules of the previous
    chapter, but it is written separately from the pass that applies them, and it shares no code with it.
    • 
  

  
These checkers earned their place while I was still writing the compiler. One optimization lets a function
  read a field without taking a reference to it, as long as the cell it came from stays alive. My first two
  versions got the liveness wrong: they released the cell just before the field was read, once in the middle
  of an instruction and once at the field read itself. On most programs, nothing visible would have happened,
  because freed memory still holds its old contents. The ownership checker rejected both versions on the first
  compile. One of the two mistakes is now a planted bug.

The same theorem, without mutation

  
The last test of the new language was to prove S(4) = 44 again. Lumen's solver from chapter 12 keeps its
  state in arrays and changes them in place. Lumen 2 has no mutation at all. So how do you write a SAT solver,
  which updates its assignment, watch lists and activity scores constantly?

  
You thread the state. The solver's whole state is one record of arrays and counters. Every function takes
  the record and returns a new one, and the code reads like a chain of updates:
  let s = assign(s, lit, reason). Semantically, each step builds a new record. But the record is
  never shared: each version is used once, to make the next. So every array_set writes in place, and
  every new record reuses the cell of the old one. The code is pure, and it runs with the cost of mutation. The
  compiler decides this, the ownership checker confirms it on every compile, and the program itself says nothing
  about memory.


  
The same proof, byte for byte

  
I ported Lumen's solver decision for decision. It uses the same order for visiting watch lists, the same
  heap of variables, the same integer activity scores, the same restarts and the same learning. The watch lists
  became linked lists inside one flat array, with new entries appended at the tail, so their order matches
  Lumen's exactly. The result is two programs, in two languages, compiled by two different compilers, that make
  the same choices. On S(4) they print the same output byte for byte: 27,684 conflicts for the split of 1 to 44,
  and the same 255,663-step refutation of 1 to 45, about 22 MB. A difference anywhere in those 22 MB would have
  pointed to a bug in one of the two compilers. The proof was then checked again, by Lumen 2's own checker.

  and 17% slower on the refutation. That depends entirely on the compiler seeing that the state is never shared. One bug showed how much: my first

The superoptimizer, again

  
I also rebuilt chapter 8's superoptimizer for Lumen 2, with new code: it searches the wasm Lumen 2 emits for
  windows of up to seven instructions with a cheaper equivalent, and proves each one with Lumen 2's own solver and
  checker. One improvement made the difference. A rule found with concrete constants is generalized: the
  constants become symbols, and the search looks for the weakest side condition under which the rule still holds.
  That is how it found its best rule, in the overflow check for multiplying by a constant, which asks whether
  the other operand lies outside a range:

  
  
This is the classic unsigned range-check trick, proved here with 17,195 checked lemmas, and it saves two
  instructions every time. With the actual constants of one program, the search first found a different
  sequence that works only for the bounds of x * 2. Searching again with the constants varied, keeping
  their signs and order, found the general form. In all, it found 19 rules.

  
They barely matter, and the reason is worth knowing. The rules remove 1.2% of the instructions in the SAT
  solver and leave its running time unchanged within measurement noise. Lumen's superoptimizer found 40 rules
  because most of its finds cleaned up after tagged 31-bit integers. Lumen 2's integers are plain 64-bit values,
  so its code generator leaves little to clean up, and the engine's own optimizing compiler already makes
  rewrites like these. The rules stay in, because they are proved and make the binaries smaller, and a planted
  bug that ignores their side conditions is caught by the eighth generated program.


  
The compiler compiles itself, again

  
The last item on the list was the one chapter 7 did for Lumen: a compiler for the language, written in the
  language. lumen2c.lm
  is about 2,800 lines of Lumen 2, with the same stages as the reference compiler: lexer, parser, type inference
  with traits, monomorphization, lowering, Perceus reference counting, code generation and a binary encoder. It
  emits the same runtime conventions, so its modules run on the same host and pass the same leak check. Without
  mutation, it threads its state through every function, as the SAT solver does, and the reference compiler turns
  that back into updates in place.

  
The test is a fixed point. The reference compiler builds stage 1. Stage 1 compiles lumen2c.lm
  into stage 2, and stage 2 compiles it into stage 3. Stages 2 and 3 are byte-identical, 287,308 bytes each, and
  each self-compilation takes under a second with nothing leaked. A fixed point alone could hide a bug that
  reproduces itself, so the modules from both stages were also compared with the reference interpreter on every
  example, the SAT solver and 1,000 generated programs. Every one printed the same output and stopped with the
  same error. That run found one bug, a trait method called on a type left undetermined, such as
  size([]), and writing the compiler found one in the reference compiler: its lowering's stack depth
  grows with the number of bindings in a function, so a list literal of about 800 elements overflows it.

  
It is a second compiler, not a copy of the first. It checks types but not effects or refinements, keeping
  every run-time check, and it makes none of the optimizations from the table above except tail calls. The SAT
  solver it compiles takes 19.6 seconds for the split of 1 to 44, against 2.4 from the reference compiler, which
  matches the 19.0 seconds the reference compiler took before those five optimizations.

What the checks caught, including my mistakes

  
    
    
  • A real bug in the reference interpreter. A random program grew a string eightfold per step.
    Compiled code stopped at the 8 MiB limit, and the interpreter kept going. The limit had never been written
    down. It is in the language spec now, and both implementations enforce it. The oracle was the one in the wrong,
    and the disagreement still exposed it.
    • 
    
  • A test suite that passed by luck. One bug I planted in the frame-clearing optimization survived
    400 random programs. A stale stack slot only causes trouble if it happens to point into the wrong half of the
    heap. That led to the paranoid mode, which poisons freed frames and validates every pointer the collector
    sees. Now that bug is caught after 8 programs.
    • 
    
  • A hole in my own optimization. The first version of frame removal treated “has no frame” and “never
    triggers a collection” as the same property. Chapter 14 tells the story. The paranoid mode caught it before
    anything was committed.
    • 
    
  • A bug in the checker's checker. The naive proof checker, written only to cross-check the fast one,
    was the one that was wrong.
    • 
    
  • A false alarm I raised myself. My benchmark harness once reported that -O had
    miscompiled the self-hosted compiler. The bug was in the harness: it deleted the baseline output before
    comparing against it. I found that before reporting anything.
    • 
    
  • A claim I had to retract. I wrote that the tail-call change made one benchmark about 30% faster.
    When I re-measured, its typical run was slower. I corrected the commit message before pushing, and the slowdown
    is documented in chapter 9.
    • 
    
  • Smaller ones, early on: a user function called run silently replaced the program's
    entry point, and two of my hand-written test expectations were wrong while the code was right.
    • 
  


  
And in Lumen 2

  
    
    
  • The oracle was wrong again. Lumen 2's interpreter compared values by plain recursion, so comparing
    two lists of 200,000 elements overflowed the JavaScript stack. The compiled code compares the last field
    with a tail call and did not overflow. The interpreter now loops on the last field too.
    • 
    
  • Counterexamples that were not real. The first refinement checker recorded the facts that define an
    if's value only inside the branch that computed it, so a nested if lost them, and the
    checker reported counterexamples that could not happen. Those facts define a fresh value and constrain
    nothing else, so they now hold everywhere.
    • 
    
  • Two liveness bugs in my own optimization, caught by the ownership checker before anything ran
    (chapter 18).
    • 
    
  • A correct optimization that made everything slower. Borrow inference copied the solver's arrays
    on every update until I changed one rule (chapter 19).
    • 
    
  • A proof checker too slow to use. The first RUP checker re-propagated every clause for every lemma,
    and took 22 seconds on a 3,665-lemma proof. With watched literals it takes 0.35 seconds. Keeping what the
    clauses alone imply between lemmas brought the S(4) check from 275 to 170 seconds.

  • An encoder that could not handle large functions. The wasm encoder appended bytes with
    JavaScript's spread syntax, which overflows the stack once a function body reaches a few hundred kilobytes.
    Replaying 200 property cases as one compiled program found it.

What this shows, and what it doesn't

  
It shows one long session of sustained engineering in which each layer was checked by the one below it. The
  work is a compiler, an independent re-implementation of it, a prover with a proof checker, an optimizer gated by
  all of them, and a theorem whose proof doesn't depend on trusting any of them. Then it is a second language,
  designed from what the first one taught, whose compiler proves parts of each program safe and checks its own
  output on every compile, which reproduced the theorem's proof exactly, and which compiles itself. Every claim on this page can be
  re-run with the commands below, which are also in the
  README. CI repeats the checks, including the
  whole proof of S(4) = 44 in both languages, on every push.

  
It does not show that earlier models could not have done this. I can't run that comparison. If you want to,
  CHALLENGE.md turns the original
  task into a benchmark with an automatic scorer. S(4) = 44 has been known since 1965; what is new here is that a
  language built in this session produced the proof, not the result itself. Lumen is also small by design: no
  floating point, no modules, 31-bit integers, and arrays as its only mutable values. Lumen 2 has no floating
  point or modules either. Its refinements are limited to linear arithmetic over integers and array lengths, and it
  reuses memory only where the size of a cell is known when compiling. Its S(4) proof rests on the same symmetry
  argument as Lumen's. And every timing here comes from one JavaScript engine on one machine.
